## How it fits together

```
apps/testbed-web (TS + Three.js)
   │  typed arrays per frame, JSON for rare calls
   ▼
crates/wp_wasm  lib.rs (wasm-bindgen, thin)  ──►  session.rs  Session (pure Rust, native-tested)
                                                    │  op log (spawn / input / reset / assists), stamped by tick
                                                    │  FixedStep accumulator, scenario scripts, hash every 60 ticks
                                                    ▼
                                                 wp_sim::Sim ──► VehicleSim / DamageSim traits (wp_vehicle, wp_damage)
```

Everything reaches vehicle and damage through `wp_sim::Sim` and the `wp_contracts` traits
(`VehicleSim::ffb`, `DamageSim::node_positions`, `Sim::vehicle_states`, …). When prompts
02/03/12 replace the stubs, **no testbed code changes**: tire forces, contacts, deformation,
health and FFB simply start showing non-trivial values.

## Exposes — WASM ABI

Car data (`data/{cars,lattices,tires,materials,modes}`) is embedded at build time by

### Layout **S** — `vehicle_states()` record (50 × f32)

| Offset | Field |
|---|---|
| 0 | entity id |
| 1–3 | pos (world, m) |
| 4–7 | rot quaternion `[x, y, z, w]` |
| 8–10 | lin_vel (world, m/s) |
| 11–13 | ang_vel (world, rad/s) |
| 14 | speed_mps (signed, chassis +Y) |
| 15 | engine_rpm |
| 16 | gear (-1 R, 0 N, 1..) |
| 17 | health 0..1 |
| 18 + 8·w | wheel w (FL, FR, RL, RR): `omega, steer_rad, compression_m, slip_angle, slip_ratio, fz_n, contact (0/1), detached (0/1)` |

### Layout **I** — `set_input()` (7 × f32)
`[steer -1..1, throttle, brake, handbrake, clutch, flags, tool_use]`; flags bits:
1 gear_up, 2 gear_down, 4 horn, 8 headlights, 16 siren. Missing trailing values = 0.

### Layout **T** — `telemetry()` (74 × f32)

| Offset | Field |
|---|---|
| 0–4 | speed_mps, engine_rpm, gear, steer_angle_rad (mean of fronts), health |
| 5–7 | accel long / lat / vert, g (chassis space, over the last tick, gravity excluded) |
| 8 | yaw_rate_rad_s |
| 9–12 | applied input: throttle, brake, steer, handbrake |
| 13 + 10·w | wheel w: `slip_angle_rad, slip_ratio, load_n, surface (index into vehicle_info().surfaces), compression_m, contact, detached, omega_rad_s, fx_est_n, fy_est_n` |
| 53–73 | component health, in `vehicle_info().components` order |

`fx_est/fy_est` are **estimates** from the tire's Magic Formula × load × surface with a
friction-ellipse cap — the contract has no tire forces yet (TB-1).

### Scenario format (`Scenario`)
A superset of simcli's `.ron`: `name, car, mode, seed, duration_s, time_of_day_h, inputs,
expect` plus the optional testbed fields `cruise_kmh` (P-controller speed hold for vehicle 1),
`others: [(car, pos, yaw, inputs, cruise_kmh)]`, `barriers: [(pos, size, yaw)]` (drawn only, TB-3)
and `pending_expect` (checked and shown, never gating — needs real physics). simcli ignores
unknown fields, so these files run in `cargo test` too. Metrics: `final_speed_mps`,
`max_speed_mps`, `distance_m`, `final_health`, `min_health`, `peak_decel_g`; prefix `vN.` for
vehicle N.

### Replay format
`b"WPR\x01"` + postcard of `Replay { header {contract_version, seed, mode, time_of_day_h,
time_ratio, scenario}, ops: [(tick, Spawn|Input|Reset|Assists)], hashes: [(tick, u64)],
view_start_tick, end_tick }`. Ops are logged from tick 0 for the whole session, only when
something changes; `record_start` only sets `view_start_tick` (playback silently re-simulates up
to it). Hashes every 60 ticks plus the final tick; playback compares each and reports
`drift_ticks`. Typical size: ~1 KB per 10 s of keyboard driving.

### How to add a debug layer
1. Add `{ id, key, label, default }` to `LAYERS` in `apps/testbed-web/src/settings.ts` — the
   hotkey, persistence and help overlay come for free.
2. Draw it where the data lives: per-vehicle in `VehicleView.update`
   (`vehicle_view.ts`), world-level in `SceneView.update` (`scene.ts`), panels in `hud.ts`; guard
   with `layers.on("<id>")` and skip the wasm call when off.
3. If it needs new sim data, add a packed getter in `crates/wp_wasm/src/lib.rs` (+ layout in
   `pack.rs`, `src/wasm/layout.ts`, and this doc), and a native test in `pack.rs`/`tests.rs`.

### How to add a scenario
1. Drop a `.ron` under `apps/simcli/scenarios/<group>/` (simcli format; see
   `crash/barrier_frontal.ron`). Gate only on what the current build can satisfy (`expect`);
   put physics-dependent targets in `pending_expect`.
2. It appears in the testbed's scenario menu immediately (the dev server lists the folder);
   the speed box overrides every `cruise_kmh` in it.
3. `cargo test -p simcli` (determinism + `expect`) and `cargo test -p wp_wasm`
   (`barrier_and_head_on_scenarios_run_and_report` covers the crash group) must stay green.

## Native testbed stub (`apps/testbed-native`)
Default build = headless smoke run printing FFB (the only thing CI builds). `--features window`
opens a winit + softbuffer window (top-down car box, 10 m grid, rack-torque bar; arrows/WASD,
Space, R, Esc). `--features ffb` opens SDL2 haptic device 0, runs one constant-force effect
updated from `rack_torque_nm / 20 N·m`, and reads joystick axis 0 as steering. softbuffer was
chosen over wgpu: no GPU or shader code is needed for a box, and it builds in seconds. Runtime
needs `libxkbcommon-x11` (X11) and, for `ffb`, `libSDL2` at link time.

## Perf numbers
Measured with `BENCH=1 npm run e2e` (bench buttons / `?bench=N`: N cars driving circles,
orbit camera, all default layers on). "sim" = `step()` wall time normalised to one 60 Hz frame
(4 physics ticks) incl. packing; "render" = JS time in `renderer.render`.

| Measurement | Machine | Native | Browser | Budget |
|---|---|---|---|---|
| sim, 1 car | cloud container, 4 vCPU Xeon 2.1 GHz, headless Chromium 141 (SwiftShader, no GPU) | – | 0.015 ms / 60 Hz frame | vehicle 0.3 ms/car (2× native) |
| sim, 8 cars | same | – | 0.031 ms | |
| sim, 24 cars | same | – | 0.054 ms | |
| render, 1 / 8 / 24 cars | same | – | 0.51 / 1.53 / 4.09 ms | |
| fps (SwiftShader CPU raster) | same | – | 13.6 / 12.7 / 11.2 | |

Stub physics makes the sim numbers meaningless as physics measurements — they show the
testbed's own overhead (session, packing, events) is negligible. Re-measure after 02/03 land
and in desktop Chrome with a GPU (the SwiftShader frame rate is CPU rasterisation, not the
testbed). Per-frame JS work scales with layers: lattice + stress layers add one 120-node /
704-beam buffer update per visible car.

## Known gaps
- Crash scenarios cannot crash yet (no vehicle bodies / static geometry in `wp_sim`); their
  `pending_expect` rows fail by design and turn green when 02/03/12 land.
- Tire forces, strain and region energy are proxies (TB-1, TB-2). FFB is 0 from the stub.
- Debug cars have no visual mesh; the skinned body uses a synthesised hull binding for grid
  lattices (`skin.ts`). A data-driven `skin_binding` without a mesh renders as points until a
  car mesh format exists.
- `set_damage_mode` restarts the session (TB-4). Replays recorded before a mode switch end at it.
- No GIF in `docs/media` (screenshots only).
- Native stub: window/FFB verified to build and open under Xvfb; FFB not tested against a real
  wheel in this environment.
